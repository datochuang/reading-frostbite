INTERACTION NET 系列・給科技業的讀者

硬體該做到哪一層

你寫的每一個程式，往下都要經過好幾層才到電晶體。每一層有自己的一套規矩，這套規矩就叫計算模型。硬體負責最底下幾層，上面的由軟體一層一層翻譯。

科技業每隔一陣子就有人想把上面某一層直接做成硬體。有人大贏，多數人輸。這一頁用這段紀錄說明計算模型是什麼。

現在又有人在下這種注：2026 年有兩家新創公司公布計畫，要把一種叫 interaction net 的計算模型直接做成處理器。頁面後半用前面的紀錄來看這個賭注，並設想它對業界的影響。

計算模型就是這樣的一套規矩。說得精確一點，它回答三件事：要算的東西長什麼樣、記在哪裡；一步是什麼；下一步由誰決定。

以 Excel 為例：要算的東西是所有格子的值；一步是重算一格；下一步由格子之間的相依關係決定，你沒有寫。

它是寫在紙上的規定，沒有規定要用什麼東西去執行。程式語言是照某一套規矩寫程式時用的寫法。

這裡的「模型」是「一套規矩」的意思。AI 說的「模型」是訓練出來的那一包參數，兩者是不同的東西。想用一個具體的題目把三件事看清楚，可以看系列的入門頁：同一張電阻網路，用三種規矩各算一次。

一疊模型

從你寫的程式到電晶體，中間隔著好幾個模型

一個模型通常交給下面那一層去執行。做法有兩種：翻譯成下一層的寫法（compiler），或是下一層有一個程式照它的規矩一步一步做（interpreter、runtime、simulator）。最底下幾層是硬體。

軟體和硬體交界的地方，這一頁叫它硬體線。線上那一層是雙方的合約：軟體保證只用合約裡列出的 instruction，硬體保證把它們做對。這份合約的正式名稱是 ISA（instruction set architecture），x86、ARM、RISC-V 都是。

下面每個例子有兩種疊法。左邊是硬體線留在一般的合約上。右邊是替上層的模型做硬體，做法有兩種：把線往上移，讓原本是軟體的那一層變成合約；或是換掉線上的模型，線的高度不變，合約換一套規矩。

贏輸被吸收：機器沒留下，想法進了主流未定

名稱它替什麼做硬體結果
  • 替一般用途的語言把線往上移，全部輸。Lisp、Prolog、functional language、Java 都有人做過。多數都做出了能動的機器或晶片。
  • 贏的有兩種。一種是把線往下移的 RISC。另一種是替特定工作換模型：GPU 與 AI 加速器。影像編解碼、網路、挖礦這些固定功能的晶片也屬於後一種，它們一直都在，沒有畫在年表上。
  • 有些想法被吸收。Dataflow 縮小之後成了 CPU 內部的 out-of-order 執行，藏在原來的合約底下，舊軟體不用改。

1980、90 年代輸的原因：一般 CPU 自己進步得太快

下面是 Hennessy 與 Patterson 整理的單核效能年增率。1986 到 2003 年，一般 CPU 每年快大約一半。

設計一顆專用晶片如果要三年：在每年進步 52% 的年代，這三年裡一般 CPU 自己變快約 3.5 倍；在每年進步 3% 的年代，只變快約 1.1 倍。（照上面的年增率換算。這份資料只到 2018 年。）

1990 年研究者 Philip Koopman 談替 functional language 做專用晶片時的說法：等這顆晶片設計、製造完，RISC 的速度大概已經快到讓這件事沒有意義。

2000 年之後輸的原因不一樣：一般程式裡找不到那麼多可以同時做的事

Itanium 和 TRIPS 都賭同一件事：把一般程式裡可以同時做的部分找出來，一次做很多。Itanium 把這件事交給 compiler。Hennessy 與 Patterson 引用 Donald Knuth 的評語：那種 compiler 基本上寫不出來。TRIPS 做出了晶片，量到的結果是編譯出來的一般程式只有當時 Intel Core 2 的 60%。

更早的量測也指向同一件事。David Wall 在 1990 年量過：一般的程式即使在很理想的條件下，平均同時能做的 instruction 大約是 5 到 7 道。

我的整理

贏和輸差在四件事

這四點是我從上面的紀錄歸納的，不是哪一份文獻的定論。每一題答「是」代表對這次嘗試有利。

1

好處跟著規模長大嗎

Lisp machine 和 Java processor 省掉的是一層翻譯的開銷，快幾倍，題目再大也是那幾倍。GPU 對大量資料做同一個運算，運算單元加倍，能同時處理的資料就加倍。研究裡報告的數字：用 GPU 訓練神經網路，2006 年的一篇是比 CPU 快 4 倍，2009 年是最多 70 倍，2011 年是 60 倍。這些數字來自不同的研究，分不出多少來自規模、多少來自 GPU 本身變好。

2

一般 CPU 已經慢下來了嗎

固定的幾倍，在每年進步 52% 的年代撐不過兩三年。GPU 通用運算在 2006 到 2007 年起步，那時單核的進步已經慢下來。

3

有真實的大量工作先付錢嗎

GPU 的研發是遊戲玩家付的；2012 年的 AlexNet 用兩張各約 500 美元的遊戲顯示卡訓練。Google 的 TPU 一做出來就有自己的服務在用。Lisp machine 得自己賣整台電腦，到 1988 年總共大約 7,000 台。政府計畫和創投的錢不算在這一題裡。

4

舊軟體不用重寫嗎

Out-of-order 藏在原來的合約底下，舊軟體完全照跑。RISC 換了合約，但程式重新編譯就好。GPU 是附掛的：其餘的程式照跑，只有要加速的那一段要改寫。Itanium 的問題是大量既有的 x86 程式在它上面跑得慢；AMD 在 2003 年把 x86 延伸成 64 位元，舊軟體照跑，市場選了後者。

最後一列是我的評估。「慢 3 到 17 倍」是和一般 compiler 產生的程式比，多半是各專案自己報的數字。

這次的賭注

Interaction net 是什麼，它主張什麼

Interaction net 是 1990 年提出的一種計算模型。程式是一張圖。圖上的元件兩兩相遇時，照一張規則表換成別的元件。它沒有「現在做到哪一行」這回事。它的規矩保證：圖上所有可以改寫的地方互不干擾，可以同時做，先做哪一個結果都一樣。

主張的好處

寫程式的人和 compiler 都不用去找「哪些部分可以同時做」，規矩本身就保證。運算單元越多，同一時間能做的改寫越多。這正是 Itanium 和 TRIPS 卡住的地方。

做 Vine 語言的 Tendrils 在一個假設運算單元無限多的模擬裡，量到同一時間平均有幾百到幾千步可以做。他們自己說這是很樂觀的上限，量的也是一個形狀規則的程式。

代價

每一步都很小，而且每一步都要配置、釋放一小塊 memory，改接幾條連線。只用一個運算單元時，它比一般做法慢 3 到 17 倍。

它也沒有 fan-out：同一份資料要用兩次就得複製，複製要算步數。

相關的幾個名字：

  • HVM：Higher Order Company 做的開源 runtime，在一般 CPU 和 GPU 上執行 interaction net。
  • Bend、Vine：寫給 interaction net 的高階語言。寫的人不用直接畫圖。
  • Tendrils Compute：做 Vine 的英國新創，2026 年 11 月募得 3,000 萬美元，要做有幾千個小核心的處理器，還沒有公布設計。
  • Architect Labs：2026 年 6 月 seed round 2,400 萬美元，11 月公布 Frostbite：用 interaction net 當合約的處理器設計。它還沒做成晶片，公布的數字來自模擬（業界叫 pre-silicon）。

放進上面的紀錄來看：它是替一般用途的程式把線往上移，也就是到目前還沒有人贏過的那一類。它主張自己不一樣的地方有兩個：好處會跟著運算單元的數目長大，以及一般 CPU 已經不再每年快一半。前一個還沒有量測可以證實。

回到名詞

所以，計算模型在產業裡是什麼

  • 計算模型是那一疊裡每一層的規矩。
  • 程式語言是照某一層的規矩寫程式時用的寫法。同一套規矩可以有很多種語言。
  • 硬體是最底下幾層的執行者。它上面的每一層，都是由下面一層的程式在執行。
  • 同一個模型可以待在不同的高度。在 HVM 裡，interaction net 是軟體層，由 runtime 執行，和 Java 的 bytecode 同一個位置。在 Frostbite 裡，它變成硬體線上的合約。

標題那個問題，到目前為止的答案：

一般用途的程式，硬體線留在低處，合約簡單，其餘交給 compiler。工作量大、形狀固定的特定工作，值得替它把線拉高，或換一個模型。

Interaction net 硬體要挑戰的是前半句。

設想

對科技業可能的影響

這一段是推論。依據是上面的紀錄，以及 Hennessy 與 Patterson 在 2018 年 Turing Award 演講（2019 年刊出）裡的論點。

已經在發生的事：特定工作的硬體改用別的模型

單核效能每年只進步幾個百分點之後，「等下一代 CPU」這條路走不通了。Hennessy 與 Patterson 主張，接下來的效能要靠替特定領域量身做的硬體，加上替那個領域設計的語言。GPU 與 AI 加速器已經照這個方向走了十幾年。對業界來說：

  • 定義合約的一方，比較留得住上面的軟體。合約不一定叫 ISA。CUDA 是 Nvidia 定的一套寫 GPU 程式的介面，作用和 x86 一樣：軟體照它寫了之後，就不容易搬走。
  • Compiler 與 runtime 變成硬體產品的一部分。一顆新晶片賣不賣得動，要看 PyTorch 這一類 framework 能不能把既有的程式自動接上去。
  • 多數軟體工程師離硬體越來越遠。大家寫的是最上面那一層。底下換硬體時，要改的部分盡量由 framework 吸收。實際上不會完全不用改，但改的量比直接寫給硬體少很多。

還沒發生的事：一般程式的那條線

Interaction net 硬體賭的是一般的程式：有很多 if、資料用指標串來串去、每一筆要做的事不一樣。這種賭注有三種可能的結局。

情境一

留在軟體層

想法被吸收，沒有新的晶片類別。

前例最多。Dataflow 進了 out-of-order CPU。Linear type（規定一份資料只能用一次的型別規則，和 interaction net 出自同一套理論）在提出大約 25 年後進了 Rust。

影響：程式語言與 runtime 多一些自動平行、不用 garbage collector 的做法。晶片業的版圖不變。

情境二

成為附掛的加速器

走 GPU 走過的路：先在某一類工作上明顯贏，裝在既有的電腦旁邊。

條件：有一類願意付錢的工作。我的猜測是每一筆要做的事都不一樣、但能拆成很多小塊同時做的工作，例如自動證明定理、自動找出符合條件的程式。Higher Order Company 這兩年就把產品轉到這個方向。

影響：多一種加速器、多一種雲端機型。既有軟體不用重寫，只有交給它的那一段要用新語言寫。

情境三

換掉一般 CPU 的合約

既有軟體要用新語言重寫。

前例是 Itanium，市場沒有等它。

影響如果發生會最大：作業系統、compiler、資料庫這些基礎軟體都要有新版本。手上有大量既有程式碼的公司，這些程式碼值多少，要看搬過去得花多少。

我的判斷：照前例，情境一最可能；情境二要看有沒有那個付錢的工作；情境三最難。要改變這個排序，需要看到三樣東西：第三方在真的晶片上量到的數字、一個有量的買家、既有軟體不用重寫就能用上的路徑。目前三樣都還沒有。

這一次和 1980 年代不一樣的地方

  • 一般 CPU 不再每年快一半。專用硬體做出來的時候，對手沒有自己變快多少。這對新的賭注有利。
  • 做晶片的時間在縮短。Google 的第一代 TPU 從設計到部署是 15 個月。Architect Labs 說 Frostbite 從架構到驗證都由 AI 完成；這是公司的說法，還沒有獨立的驗證。如果成立，「專用機器要做好幾年」這個老問題會變小。
  • 搬軟體的成本有可能下降。把既有程式改寫到新語言，過去沒有人願意付這筆錢。AI 寫程式的工具也許會改變這一點，目前沒有證據。

和以前一樣的地方

  • 每一步的固定開銷還在。把上層模型做成硬體，省掉的是一層翻譯。模型本身規定要做的事一樣要做：在 interaction net 是每一步配置、釋放 memory 和改接連線。
  • 一般程式裡有多少事可以同時做，還是沒有定論。Itanium 和 TRIPS 都卡在這裡。
  • 市場不等人。Hennessy 與 Patterson 回顧 Itanium 這類例子時寫的是：市場很少有耐心。

對不同角色

角色現在就相關的情境二或三發生的話
IC 設計加速器的設計與驗證已經是日常。合約怎麼定，是架構師最重要的決定要驗證的不再是一串 instruction 的行為，而是一張圖怎麼被改寫。現有的驗證方法要重想
Compiler 與語言把上層模型接到各種硬體，決定新硬體賣不賣得動新語言，以及新的除錯工具。這種模型沒有 call stack，現有的 debugger 用不上
軟體開發選 framework 時，留意它能不能把同一份程式送到不同的硬體上。能的話，底下換硬體時你要動的很少情境二：多數人感覺不到，由 library 處理。情境三：要學新語言
評估這類公司的人問三件事：有沒有第三方在真的晶片上量到的數字；買家是誰、量有多大；既有軟體怎麼搬。公司自己公布的 pre-silicon 數字不能當結論
